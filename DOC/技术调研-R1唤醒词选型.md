## 1. 三方案对比

| 维度 | sherpa-onnx KWS | openWakeWord | Porcupine (Picovoice) |
|------|-----------------|--------------|----------------------|
| 许可 | Apache 2.0 完全开源 | Apache 2.0 完全开源 | 专有软件；**免费档 2026-06-30 已关停**，商用需付费（报价数千美元级） |
| 中文支持 | ✅ 中文/中英双语预训练模型（WenetSpeech 1万小时语料） | ⚠️ 原生英文；中文需自组训练管线（依赖中文 Piper TTS 造合成数据，社区实测"踩坑之旅"） | ✅ 官方支持普通话，Console 训练 |
| 自定义唤醒词 | ✅ **改 keywords.txt 即可，无需训练**（text2token 转拼音音素） | 需训练（Colab 上数小时，含数据生成） | Console 网页训练，但现在要付费 |
| 本机依赖 | **零新增**（1.13.6 已含 API） | +onnxruntime+训练链路 | +pvporcupine SDK + AccessKey（联网激活） |
| 离线 | ✅ 完全离线 | ✅ 完全离线 | ⚠️ AccessKey 需联网验证 |
| 模型体积 | 18–38MB（int8 可减半） | ~1–2MB | 小 |
| 精度调参 | keywords_threshold / keywords_score 可调，中文音素级匹配 | 阈值可调但中文音系（声调、同音音节多）未针对性设计 | 宣称 97%+（英文场景） |
| 风险 | 音素序列对多音字/儿化音敏感，需实测调阈值 | 中文误唤醒率无先例保障 | **免费通道已死，个人项目不可用** |

### 各方案细节

**sherpa-onnx KWS**
- 预训练模型二选一：
  - `sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20`（中英双语，38MB，chunk-8 延迟 160ms / chunk-16 延迟 320ms）
  - `sherpa-onnx-kws-zipformer-wenetspeech-3.3M-2024-01-01`（纯中文，18MB，WenetSpeech L 子集训练）
- 自定义词三步（无需训练）：
  1. 写 `keywords_raw.txt`：`小学习 @小学习`
  2. `sherpa-onnx-cli text2token --tokens-type phone+ppinyin` 转音素
  3. 运行时传 `keywords_file`
- 关键参数：`keywords_threshold=0.25`（默认）、`keywords_score=1`、`num_trailing_blanks=1`
- 已知坑：多音字需手工核对生成的拼音序列；chunk-8 低延迟但精度略降

**openWakeWord**
- 优点：真开源、模型极小、Home Assistant 生态成熟、openwakeword.com 平台号称支持 20+ 语言
- 缺点（针对本项目）：
  - 训练管线围绕英文 Piper TTS 合成数据设计，中文需自己找中文 Piper voice 造数据
  - 声调语言 + 同音音节密集的中文场景无针对性优化，误唤醒率没有保障先例
  - 训练迭代周期（数小时/轮）vs sherpa 改文本秒级生效

**Porcupine**
- 工程质量最好（精度、CPU 占用、跨平台），但：
  - **免费档 2026-06-30 已停**（今天 2026-10-16，已过期 3.5 个月），现有 Free AccessKey 已失效
  - 商用/个人持续使用均需付费，与本项目全本地开源栈的定位冲突
  - AccessKey 需联网激活，违背 NFR1（全链路本地/局域网）

## 2. 推荐方案：sherpa-onnx KWS 集成设计

### 2.1 架构（复用现有 mic_loop，不另开音频流）

```
mic_loop 音频块 (512 样本)
   │
   ├─ ACTIVE 状态 → 现有 VAD→ASR 管线（不动）
   │
   └─ IDLE 状态 → KeywordSpotter.accept_waveform()
                    → is_ready / decode_stream → 命中 → 切 ACTIVE
```

关键决策：**不另开麦克风流**。KWS 与现有 VAD 共用同一条 `sd.InputStream`，按状态机分流音频块，避免两个流抢 ALSA 设备（本机单设备，双开必挂）。

### 2.2 状态机

```
IDLE ──唤醒词命中──→ ACTIVE（播提示音"我在"）──30s无有效语音──→ IDLE
                        │
                        └─ 现有 VAD→ASR→LLM→TTS 全流程照旧
```

实现落点：`SmartSpeakerASR.mic_loop` 内加 `self.state` 分流；`voice_chat.py` 的回声门控逻辑原样保留（ACTIVE 内 TTS 播报照旧 mute/unmute）。

### 2.3 实施步骤

1. 下载模型到 `models/kws/`：先试 wenetspeech-3.3M（纯中文、更小）
2. 编写 `src/voice_input/kws.py`：`KeywordSpotter` 封装（init / process_block → Optional[hit_word]）
3. `vad_asr.py` mic_loop 加状态分流 + IDLE→ACTIVE 转换 + ACTIVE 超时回退
4. `voice_chat.py` 加唤醒提示音（复用 TTS 合成短句或预生成 wav，避免每次合成）+ `--wake-word` / `--no-wake` CLI 参数（关掉即回到当前开放麦克风模式）
5. 用 `test_output.wav` 类回放样本做误唤醒/漏唤醒测试（FR1.5）

### 2.4 验收对齐（需求文档 R1）

- [ ] IDLE 下普通对话不触发 LLM（KWS 拦截在 ASR 之前）
- [ ] 3m 内正常音量唤醒成功率 ≥95%（实测阈值调到满足为止）
- [ ] 唤醒→提示音 ≤ 0.5s（chunk-8 模型延迟 160ms + 提示音预生成）
- [ ] 状态切换有日志与提示音

## 3. 待定项

1. 唤醒词选词（建议 3–4 音节、避免日常高频词；先用"你好伙伴"类占位实测）
2. 模型选 chunk-8 还是 chunk-16（先 chunk-16 测精度，不达标再降延迟）
3. ACTIVE 超时 30s 是否需要"快睡了"二次提醒音
