## 1. 目标与结果

**最终结果**（离线验证，驱动真实集成代码路径）：

| 指标 | 标准 | 实测 |
|------|------|------|
| 插话检测延迟 | — | 0.16s（含 96ms 三连帧防抖） |
| 停播耗时 | — | 3ms（abort 清输出缓冲） |
| **端到端（开口→静音）** | ≤0.5s | **≈0.17s** ✅ |
| 回声残留比用户语音 | ≤-20dB | -25 ~ -37dB ✅ |
| 纯回声误触发 | 不触发 | 0 次（100/200ms × 0.3/0.6 衰减全组合）✅ |
| 延迟提示依赖 | — | hint=0（内部估计器）与精确 hint 等效 ✅ |

## 3. 问题解决实录（按时间顺序）

### P1 首轮全 FAIL：回声区 VAD 概率 0.64~0.98 全线爆表

**现象**：第一版测试跑完，7 个组合全部 FAIL。RMS 抑制本身达标（100/200ms 组合残留 -22~-37dB），但 `p_回声`（回声区 webrtc VAD 概率峰值）0.64~0.98——比插话区还高，看似"AEC 没用"。

**发现过程**：对比表格发现矛盾点——RMS 说回声被压掉 20-37dB，VAD 却说满屏语音。两个指标必有一个在撒谎。

**分析**：逐项审查测试脚本，找到两个测试缺陷：

1. **统计包含了 AEC 收敛期**。自适应滤波器启动后需要约 0.5s 学习声学路径，收敛前的残留很大。我的统计只排除了前 0.05s，收敛期的"高概率块"被计入了稳态误报。
2. **更根本的：合成混音没有噪声底**。真实房间里麦克风永远有风扇/电流/环境噪声（典型 -45dBFS）。我的合成 near = 纯回声 + 纯人声，静音段是数学意义上的绝对零。AEC 残留哪怕压到 -50dB 也远高于"零底"——任何 VAD 面对高于底噪的信号都会报语音。**这不是 AEC 不好，是我造了一个物理上不存在的房间。**

**实验**：加 `-45dBFS` 高斯噪声底（固定种子保证组合间可比）、统计排除前 0.5s 收敛期。

**结果**：误报大幅下降，方向确认。此问题暴露的核心教训：**测试环境必须模拟真实物理条件，否则测的是幻觉。**

### P2 "保留dB" 全 FAIL：判据本身设计错了

**现象**：第二轮测试，误报指标好转，但"插话保留dB"（AEC 后用户语音相对 AEC 前的保真度）全部 -4~-10dB，按原标准（>-3dB）全 FAIL。

**发现过程**：检查数字本身——用户语音经过 AEC+NS 后衰减了 4-10dB，这个数字是真实的、符合信号处理常识的（自适应滤波器对近端信号有侵蚀，NS 也会压低电平）。

**分析**：问题不在信号，在**验收标准的定义**。回头审视架构设计：clean 信号只用于**打断判定**（触发停播），用户被打断后重新说话，ASR 走停播后的正常麦克风管线——**clean 信号从来不进 ASR**。既然不用于识别，"保真度"就无关紧要，silero 能不能从中检出语音（检出率）才是关键指标。

**解决**：删掉"保留dB"门（保留为信息展示），判据改为：残留比 ≤-20dB、误报 <2%、（后来加的）首触发 ≤0.3s。

**教训**：验收指标必须和信号的真实用途对齐。为不进入 ASR 的信号设保真度门槛，是拿错尺子量错东西。

### P3 首触发 0.73~0.86s：silero 在用"为 ASR 设计的参数"做打断判定

**现象**：第三轮测试（判据修正+双轨 VAD 后），误报、残留全过，卡在首触发 0.86s，标准 ≤0.3s，超 3 倍。

**发现过程**：延迟预算拆解——块粒度 32ms + silero 推理本身毫秒级，凑不出 0.86s。缺口必然来自配置。

**分析**：检查喂给 silero 的配置，发现照抄了主 VAD 的 `min_speech_duration=0.25s`。这个参数的含义是"语音持续 250ms 才确认是语音"——它是为 **ASR 断句**设计的（避免把咳嗽、桌椅碰撞切成"一句话"送去识别，识别错了代价高）。但**打断判定恰好相反**：宁可错杀（用户其实没想打断，损失是重听半句）不可漏杀（用户喊停没反应，体验崩坏），而且停播这个动作代价极低、完全可逆。

**解决**：barge 专用 silero 实例独立配置：`min_speech_duration=0.06s`（2 块）+ `min_silence_duration=0.3s`，防抖交给独立的"3 连帧"判定（96ms），与 silero 内部参数解耦。主 VAD 参数原样不动（两套职责，两套参数）。

**结果**：首触发 0.86s → 0.63s。同一个模型，参数对齐用途后行为完全不同。

### P4 首触发仍 0.63s：度量原点错在"混音位置"而非"实际开口"

**现象**：P3 修正后 0.63s，仍超标 2 倍。

**发现过程**：继续做延迟预算拆解时起疑：32ms 块 + 60ms 确认 + AEC 因果性，物理下限约 0.2s，0.63s 里多出的 0.4s 是什么？怀疑计量起点有偏。

**分析**：`t_first` 从**混音插入位置**（t=1.0s）起算，但插入的用户 wav（KWS 模型自带 3.wav）开头不是语音——它是真人录音，有前导静音。先用滑窗 RMS（20ms 窗、超噪声底 20 倍判定开口）量出 3.wav 的实际语音起点：**0.56s**。真实检测延迟 = 0.63 - 0.56 ≈ **0.07s**——不是系统慢，是尺子刻度错了 0.56s。

**解决**：`speech_onset()` 函数自动检测插话 wav 的开口时刻，`t_first` 以此为原点。顺带清理了度量代码。

**结果**：首触发修正为 0.07~0.10s，富余 3 倍。此问题和 P1 的噪声底、P3 的参数同属一类：**离线度量的参照系必须校准到物理事实**。

### P5 200ms/0.3 组合误报 6.2%：灵敏度与鲁棒性的最后一格

**现象**：P4 修正后仅剩一个 FAIL：200ms 延迟 × 0.3 衰减（弱回声、抑制余量最小的组合）误报 6.2%，超 2% 标准三倍。

**分析**：这是 P3 把 min_speech 从 0.25 压到 0.06s 的副作用——判定变快的同时变敏感，最弱抑制组合的残留刚好够到旧阈值 0.6 的触发线。这是典型的灵敏度-鲁棒性交换，还剩两个旋钮：silero 阈值（0.6→0.7）和防抖帧数（3→4）。

**实验**：先试代价小的——阈值 0.6→0.7（防抖加帧会让首触发多 32ms 且治标不治本）。

**结果**：200ms/0.3 误报 6.2%→0.3%，其余组合 0%，首触发只涨到 0.07~0.16s，仍富余近一倍。**全组合 PASS**。确定 0.7 为默认值（写进代码默认参数与文档）。

### P6 400ms 延迟误报 70%：AEC3 规格边界，界定范围而非"解决"

**现象**：400ms 组合误报 67~70%，无论怎么调参都压不下来。

**分析**：查证后确认这不是调参问题：WebRTC AEC3 的延迟处理规格覆盖约 300ms 内，400ms 超出设计范围，滤波器对不上回声路径，残留自然大。而**本方案的实际声学延迟** = ChunkedPlayer 输出缓冲（blocksize 512，约 32-64ms）+ 声传播（<10ms）+ 输入缓冲（32ms）≈ **70-130ms**，留一倍余量到 200ms 已经充分。

**解决**：测试工具把 >200ms 标注"超规格"（不进 GO 门但保留展示，作为边界档案）；GO 判定只覆盖实际部署会出现的延迟范围。**不是所有 FAIL 都要修——先问这个场景是否真实存在。**

### P7 ChunkedPlayer 自测崩溃：abort() 打断阻塞中的 write 抛异常

**现象**：Phase B 自测，3s 扫频完整播放通过；但"1s 后 stop"场景直接抛 `PortAudioError: File descriptor in bad state [ALSA error -77]`。

**发现过程**：自测的第二项就是专门验证停播路径的（`threading.Timer(1.0, player.stop)`），一跑就崩。

**分析**：读堆栈定位到 `stream.write()`。机制：`stop()` 在另一个线程调用 `stream.abort()`，PortAudio 立即拆除流，此时**正在阻塞写出的 write() 被强制唤醒并以错误码返回**。这不是 bug——这正是 abort"清空缓冲立即静音"的实现方式。异常就是停播的信号本身。

**解决**：play 循环里捕获 `sd.PortAudioError`：若 `_stop_evt` 已置位 → 返回 False（正常被打断语义）；未置位才重新抛出（真错误）。顺带确认了时序：stop 后 play() 在 **3ms** 内返回——这就是 FR2.2 的停播耗时。

### P8 离线端到端测试插话不触发：墙钟豁免 vs 加速回放

**现象**：Phase C 集成完成后，写了一个直接驱动真实 `_barge_check()` 方法的离线闭环测试（绕过麦克风）：纯回声 0 误触发 ✅，但**插话也一次都没触发** ❌。而同样的信号在 Phase A 测试工具里是能触发的。

**发现过程**：两套测试用的信号完全相同，差异只能在代码路径。逐行对照 `_barge_check` 与 Phase A 的循环，锁定这一行：

```python
if time.time() - self._play_t0 < 0.6: return   # 收敛期豁免
```

**分析**：收敛豁免用的是**墙钟时间**。真实播放是实时流，墙钟 0.6s = 音频 0.6s，逻辑正确。但离线测试以 CPU 速度灌块——19s 音频约 2s 就跑完了，用户插话发生在音频第 1.56s 处，此刻墙钟才过了约 0.2s，**整段插话全落在 0.6s 豁免窗内**，一次判定都没执行。又是"离线加速回放与实时语义错位"这一类问题（与 KWS 的尾部静音坑同源）。

**解决**：测试侧把 `asr._play_t0` 拨到过去（`time.time() - 10`）绕过豁免；生产代码不动（实时播放下逻辑正确，且 0.6s 豁免是 P1 验证过的必要保护）。

**结果**：插话 0.16s 触发、纯回声 0 误触发，端到端闭环验证通过。

## 5. 方法论沉淀

1. **离线先行，风险前置**：最不确定的假设（AEC3 在本机条件下是否可用）最先用零侵入的离线实验验证，四天里 8 个问题有 6 个在离线阶段暴露，无一流入生产代码。
2. **指标矛盾即线索**：RMS 说好、VAD 说坏（P1）→ 必有一个度量在撒谎，追矛盾比追数字快。
3. **指标对齐用途**：为"只做判定、不做识别"的信号设保真度门（P2）、为"求快不求稳"的场景用"求稳"参数（P3），都是尺子用错。
4. **离线模拟三要素**：噪声底要真实（P1）、时间原点要物理（P4）、墙钟与音频时钟要区分（P8）。
5. **FAIL 先分真假与范围**：先问"场景是否真实存在"（P6 超规格）再问"怎么修"；不是所有 FAIL 都值得修。
6. **每个坑回归可查**：`test_aec.py` 保留全部修正与扫描能力，参数改动可一键回归。

## 6. 遗留事项

- **Phase D 真机验收**（需用户执行）：打断端到端延迟、连续播报误打断统计、打断后追问与"刚才说到哪"、Ctrl+C 回归。调参入口：`--barge-threshold`（误断多→0.8，不灵敏→0.6）
- 双设备时钟漂移的长播报（>60s）专项：AEC3 每次播报 reset + 参考按样本数对齐已做设计防御，待真机长回答验证
- R3 流式响应直接复用 ChunkedPlayer，播报层无需再动
