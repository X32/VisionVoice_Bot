# R3 流式响应 技术方案

## Context（为什么做）

需求文档 FR3.1-FR3.4：当前首响应延迟 = LLM 全量生成 + TTS 全量合成 + 播放，长回答体感 5s+。
目标：LLM 流式输出 → 按句增量 TTS → 边合成边播放，**30 字回答首语音延迟 ≤ 2s**，长回答无句间长停顿，打断时立即终止上游 LLM 生成与 TTS 合成。

R2 已铺好地基：ChunkedPlayer 分块流式播放（play/stop/on_chunk）本就按"R3 流式底座"设计；
打断判定链（mute/set_playing/feed_reference/_barge_check）语义天然覆盖长播放会话，**vad_asr.py 零改动**。

## 现状关键事实（已勘察）

- `unified_llm.py`：三端点全 urllib + `"stream": False`。Ollama `/api/chat`（流式=NDJSON 行，
  tool_calls 在某块 message.tool_calls 里，qwen 通常首块即到且 content 为空）；llama.cpp/OpenAI
  `/v1/chat/completions`（流式=SSE `data:` 行，delta 在 choices[0].delta）。客户端断开连接 → ollama 取消生成。
- `player.py ChunkedPlayer.play()`：每次调用新建 OutputStream（句间连播会有开流间隙）；
  writer 线程 + 三态有界返回（完成/stop+150ms/超时）骨架可复用。
- `test_tts.py TTS.speak(play=False)`：sherpa OfflineTts 整句合成，22050Hz 输出，
  短句 gen_time 约 0.3~0.8s（RTF<1）。单线程使用，无并发问题。
- 打断链：`_barge_check` 在 `_ref_buf` 为空时自动跳过（播报未开始不误判）；0.6s 收敛窗被
  0.5s primer 静音覆盖；`set_playing(True)` 重建 AEC/KWS 防状态污染——全部按"每次播放会话一次"设计，
  流式会话沿用同一生命周期。

## 方案总览（数据流）

```
worker线程                合成线程(新)                播放writer线程
─────────────────────────────────────────────────────────────────
LLM chat_stream 增量delta
  → SentenceSplitter攒句 ──→ sentence_q(maxsize=2)
  （同步攒全文）               → tts.speak(句)        ──→ play_segments迭代器逐段取
                              → 重采样16k+trim           → 按BLOCK写OutputStream
                              → 段落入队(背压)            → on_chunk喂AEC参考
最终句/流结束 → 哨兵None ──→ 退出                        → 播完/被打断返回
```

- 首句攒到即合成即播（首延迟 = 首token延迟 + 首句生成 + 一次短句合成）
- 合成线程提前合成下一句（maxsize=2 背压）→ 句间无空洞
- 打断（任意时刻）：`interrupted`标志 + `player.stop()` + LLM 流 `gen.close()`
  （→urllib resp.close() → ollama 服务端取消生成）+ 清空句子队列 + 合成线程退出

## 改动清单（4 个文件，vad_asr/kws/TTS 类零改动）

### 1. `src/llm/unified_llm.py` —— 三端点加 `chat_stream()`

- `OllamaEndpoint.chat_stream(messages, tools=None, **kwargs)`：`/api/chat` + `"stream": True`，
  `urlopen` 后逐行 `resp.readline()` 解析 NDJSON：
  - `message.content` 非空 → `yield {"delta": text}`
  - `message.tool_calls` → `yield {"tool_calls": [...]}`（同现有解析格式）后结束
  - `done:true` 行 → `yield {"done": True, "text": 全文, "usage": {...}}`
- `LlamaCPPEndpoint.chat_stream()` / `OpenAIEndpoint.chat_stream()`：SSE 解析
  （`data: {...}`，`choices[0].delta.content` / `delta.tool_calls` 片段聚合，`data: [DONE]` 结束），
  消息格式与二者现有非流式 generate(messages=...) 完全一致
- 生成器 finally 里 `resp.close()`——消费方 `gen.close()`/break 即取消上游生成
- `LLM.chat_stream()` 门面分发（同 chat() 的后端分派逻辑）
- 现有 `chat()/generate()` 不动（工具重试等仍可用）

### 2. `src/tts/player.py` —— ChunkedPlayer 加 `play_segments()`

```python
def play_segments(self, segments, on_chunk=None, no_progress_timeout=30.0) -> bool
```
- `segments`: 惰性迭代器，产出 16k float32 段落（提前处理好的）；writer 线程边取边写，
  阻塞 get 天然形成生产背压
- 复用 play() 的 writer 骨架：BLOCK 补零、on_chunk 回调、PortAudioError=被打断、
  `stop()` 只置事件+异步 abort、play 本体三态有界返回
- 差异点：① 首段前置 0.5s primer（只垫一次，后续句不垫）② 总时长未知 →
  超时改为**无进展超时**（上次成功写入后超过 30s 无新段落 → ⚠️ 告警返回 False，
  覆盖 ALSA 写停滞 + LLM 中途僵死两种情形）③ 迭代器抛异常 → 记错误返回 False
- 全程持 `self._lock`（与 play() 互斥，防御并发）
- `play()` 原样保留（唤醒/待机短句继续用，零回归）

### 3. `src/chat/voice_chat.py` —— 句切分 + 流式 worker 管线

**SentenceSplitter 类**（纯逻辑，可单测）：
- 边界规则：`。！？!?；;\n` 必切；`，,` 在缓冲 ≥10 字时切（首句尽快出声）；缓冲 ≥60 字强切（无标点兜底）
- 过滤：markdown 符号(`#*>\`[])剥离、纯符号/空白段跳过、每句过 `tts_sanitize()`
- `feed(delta) -> list[句]` + `finish() -> 尾句`

**worker 流式管线**（替换现有"全量合成后播放"段；`--no-stream` 可回退旧路径）：
- `mute()` → `_chat_with_tools_stream()`：
  - 每轮 `llm.chat_stream(history, tools, temperature=0.3)`；增量文本实时打印（打字机效果）
  - 攒句 → 塞 `sentence_q`；**检测到 tool_calls**：`gen.close()` 取消上游 → 执行工具 →
    下一轮（qwen 工具调用首块即到、content 为空，说出口的碎片概率极低；万一有，属
    "让我查一下"类无害文本，记入该轮 assistant 历史）
  - 乱码防御改造：逐句检查 `_looks_garbled`，乱码句跳过不合成（记历史）；
    整响应乱码且**尚未说出任何内容**时保留原降温重试逻辑
  - 合成线程：`sentence_q.get()` → `tts.speak(句, play=False)` → 重采样16k + trim →
    段落队列（maxsize=2 背压）；哨兵/打断时退出
  - 首段就绪前调 `set_playing(True)` → `player.play_segments(段迭代器, on_chunk=feed_reference)`；
    结束 `set_playing(False)` + `unmute(打断0.3s/正常mute_tail)`
- **打断联动**：`interrupted` 标志在 delta 循环、句切分、合成线程、播放四处检查；
  命中任一 → 停止喂句 + `gen.close()` + 队列清空 + player 已由 on_barge_in stop
- **历史记录维持 R2 决策不变**：被打断仍记**全文** + "（被用户打断）"标记
  （全文使模型被问"继续"时能接着说，优于只记已说部分）；worker 开头保留
  `state=='idle'` 待机竞态守卫
- 工具轮不说话的场景：mute→流式→无文本→unmute 快速往返，行为等价现状

### 4. 新增 `src/chat/test_stream.py` —— 离线验证（R2 test_aec/test_barge 同风格）

- **A 句切分单测**：标点切分/首句逗号提前/无标点60字强切/markdown剥离/纯符号跳过/尾句flush
- **B 假LLM脚本化E2E**：预设 delta 序列（带延时）驱动真实 Splitter+TTS+ChunkedPlayer：
  首语音延迟、句间 gap（目标 ≤0.3s）、长回答完整性
- **C 打断演练**：播放 1s 时置 interrupted+player.stop() → 断言：上游生成器已 close、
  合成线程退出、≤0.3s 静音、历史为全文+打断标记（R2 行为不变）
- **D 真实 ollama 延迟探针**（需 ollama 在跑）：测 TTFT + 首句边界时间 + 单句合成时间，
  验证 30 字回答首语音 ≤2s 的预算拆解
- 回归：`player.py main()` 自测（play() 短句路径不变）、`test_barge.py` 五场景重跑（vad_asr 未动，应全 PASS）

## 已知边界（诚实清单）

- 首句出口前（约 1~1.5s 纯 LLM 阶段）无法打断——AEC 参考未到，`_barge_check` 跳过
  （与现状"思考中不能打断"一致，但窗口从 5s+ 缩到 ~1s）
- 逐句合成导致句间音量按句归一化，可能有轻微响度差（matcha 每句峰值归一化；接受）
- 单音节/超短句合成质量：切分保证最小句长 ≥2 字，无此风险
- OpenAI 远程端点流式已实现但验收仅测 ollama（本地链路为准）
