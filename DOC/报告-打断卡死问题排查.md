# 问题排查报告：打断功能三次真机冻结的定位与根治

> 项目：learnPartner ｜ 关联：`DOC/报告-R2.1打断语义化.md`（打断功能本体）
> 日期：2026-10-17 ｜ 状态：三层防御全部就位，离线/冒烟验证通过，待真机复测
> 问题：语音打断（barge-in）功能在真机上连续三次导致整个助手冻结

---

## 1. 问题定义

**现象**：真机运行 `voice_chat.py`，机器人播报中用户打断，日志打出：

```
✋ 打断(stop_word:不要说了)，停止播报
```

之后系统永久冻结：不再播报、不再识别语音、不听任何指令，只能杀进程。

**关键观察**：三次冻结全部发生在**打断瞬间**（long_speech / stop_word 两种通道都出现过），正常对话不冻结。日志都停在打断打印，见不到后续应有的"✋ 播报被打断"——说明冻结点在打断打印与播报收尾之间。

**架构上下文**（理解排查的前提）：

```
mic_loop线程                          worker线程
  读麦克风→队列→消费                    LLM→TTS合成→ChunkedPlayer.play()
  ├ 回声门控(mute窗口丢弃)                ├ 每块写OutputStream + 回调far-end参考
  ├ _barge_check(AEC→KWS/silero)        └ 播完/被打断 → unmute(恢复收音)
  │    └ 命中→on_barge_in→player.stop() ↘
  └ VAD断句→ASR→队列→worker              unmute由worker在play返回后执行 ★
```

★ 是致命依赖：**恢复收音（unmute）依赖 worker 从 play() 返回**；而**打断判定（_barge_check）运行在 mic_loop 线程**。任何一条线程被永久卡住，mute 窗口就永远不关，系统假死。

## 2. 根因总览

三冻结同根：**双工 ALSA 下，PortAudio 的 C 调用会间歇性永久阻塞**——不抛错、不超时、永不返回。同一个底层数据一致性/设备状态问题在三个调用点露出三张面孔：

| # | 触发调用 | 所在线程 | 后果 |
|---|---------|---------|------|
| 1 | `InputStream.read()`（读侧停滞） | mic_loop | 收音循环卡死 |
| 2 | `OutputStream.abort()`（stop 内同步调用） | mic_loop（经 on_barge_in） | 收音循环卡死 |
| 3 | `OutputStream.write()`（流被 wedge 后） | worker（play 内） | play 永不返回 → unmute 永不执行 |

历史佐证：这不是新问题——`voice_chat.py` 的 SIGINT 看门狗注释里早就记录了"Pa_ReadStream 会间歇性停滞，主线程卡在 C 调用里永不返回"。当时它只在**退出**时咬人（所以有 `os._exit(0)` 硬退出兜底）；R2 让"播放中持续收音 + 打断时 abort 流"成为常态后，它在**运行中**发作，且原看门狗管不到运行路径。

## 3. 排查与修复过程（三轮）

### 第一轮：读侧停滞 → reader 线程解耦 + 自愈重建

**假设与实验**：先排除逻辑层——`stop()` 离线自测 1ms、`play()` 正常返回，打断逻辑本身无死锁。复现关键在**线程拓扑**：`stop()` 由"正在读麦克风的线程"调用（Timer 线程调用则不复现），且输入流打开（双工）。复现结果呈**间歇性**：同脚本第一次 mic 线程停滞 >6s、第二次 250 次读全部正常——与看门狗注释记录的间歇性吻合，锁定读侧。

**修复**（`vad_asr.py` mic_loop 重构）：

```
_reader线程(新增): 阻塞read塞队列          ← 停滞时此线程被牺牲
mic_loop: 队列消费(2s超时)
   ├ 正常: 原有 门控/唤醒/打断/VAD 逻辑零改动
   └ 超时/读错 → daemon关流 → 清全部检测器状态
             → 重建InputStream → 继续对话    ← ~2.5s自愈
```

**验证**：假流模拟 read 永久阻塞 → 9s 内 3 轮自愈、mic_loop 存活；真机 6s 冒烟无告警。

### 第二轮：stop 内同步 abort 阻塞 → 异步 abort

**现象**：读侧修复后，`stop_word:你好小迪` 打断再次冻结——读停滞看门狗没防住。

**分析**：卡点换了地方：`on_barge_in` 在 mic_loop 线程里同步调 `player.stop()` → `stream.abort()`，这个 C 调用同样会间歇性永久阻塞。看门狗只盯队列读取，防不住 `_barge_check` **内部**的阻塞。

**修复**（`player.py` stop）：`stop()` 只置事件、立即返回；`abort()` 扔进 daemon 线程执行。写循环靠事件检查退出（每块之间），即使 abort 永不生效，缓冲排空后也自然停。

**验证**：自测 stop 后 play() 4ms 返回。

**为什么没根治**：abort 异步化只保证"调 stop 的线程不被卡"，但流本身已被 abort/设备状态问题 wedge——见第三轮。

### 第三轮：write 卡死在 wedge 的流上 → play() 有界返回（最终版）

**现象**：异步 abort 后，`stop_word:不要说了` 打断**仍然**冻结。

**推理定位**（这次无法直接复现，靠日志缺口+代码走查推理）：日志停在打断打印、没有"播报被打断"——worker 卡在 `play()` 内部。唯一能永久阻塞的点是 `stream.write()`：流被 wedge 后，write 阻塞在 C 调用里**永不出错**（abort 没有生效到唤醒它），play() 永不返回 → unmute 永不执行 → mute 窗口无限 → mic_loop 即使自愈了也在丢弃所有音频 → 系统静默假死。前两轮修复都在别的线程，worker 这条线没有任何逃生门。

**修复**（`player.py` play 重构）——**返回有界保证**：

```
writer线程(新增): 实际写循环（可能被卡死，被牺牲）
play(): 只等三态之一
  ├ 写完          → True
  ├ stop(+150ms)  → False
  └ 超时(时长+2s)  → 打"⚠️播放写线程停滞"告警 → False   ← 逃生门
worker: play无论哪种情况都拿到返回 → set_playing(False) → unmute执行
```

**验证**（三态自测）：
- 正常播放 3s 音频 → 2.9s 返回 True ✅
- 播放 1s 处 stop → 即时返回 False ✅
- monkeypatch 模拟 `write()` 永久阻塞 → **3.0s 超时逃逸返回 False** ✅

`test_barge.py` 五场景全套回归 PASS。

## 4. 最终防御体系

```
                       任何C调用被卡 → 所在线程被放弃(daemon) → 状态逃生门
┌─────────────────────────────────────────────────────────────┐
│ mic_loop线程                                                  │
│   队列get 2s超时 ──停滞──→ 重建InputStream（收音恢复）          │
│   on_barge_in→stop(): 置事件即返，abort在daemon               │
│ worker线程                                                    │
│   play(): 写完/stop/超时(时长+2s)三态有界返回                   │
│     → unmute必达（mute窗口必关，收音必恢复）                     │
│ 被牺牲者: _reader线程 / abort线程 / writer线程 / 旧流           │
│          (全部daemon，进程退出时os._exit(0)硬退不清理)          │
└─────────────────────────────────────────────────────────────┘
```

**核心原则**（写进 memory，后续所有音频代码遵守）：
1. **任何线程不允许无限期阻塞在 PortAudio/ALSA 的 C 调用上**——读、写、abort、close 都可能卡
2. **关键路径（unmute/收音恢复）必须有超时逃生门**，不依赖任何单次 C 调用返回
3. 阻塞式 C 调用只允许出现在**可牺牲的 daemon 线程**里
4. 每层防御独立生效：读侧自愈、stop 异步、play 有界——任何一层失守，其余两层仍保系统存活

## 5. 遗留风险与后续方向

| 风险 | 现状 | 后续 |
|------|------|------|
| wedge 的流/线程泄漏（每次冻结演变为一次卡顿+泄漏） | daemon 化，进程内不致崩溃 | 若停滞告警频繁，需根治 |
| ALSA 间歇阻塞的底层原因（HDA 双工 + power_save） | 绕行而非修复 | 可试 `power_save=0`（此前首字丢失问题的同源配置）；或换 ALSA 配置/ dmix |
| sounddevice 阻塞式 API 的天然风险 | 三层逃生门兜底 | **根治方案：改 callback 模式**（输入输出流都用回调，不自己调 read/write/abort）——改动大，作为下一阶段候选 |
| 打断后 far-end 参考与实际播出错位（wedge 时参考多喂） | AEC3 每次播报重建，可吸收 | 观察 |

**真机复测判据**：
- 正常情况：打断 → 停播 → 对话继续，无告警
- 最坏情况：打断 → 卡顿 ≤2s + 出现 `⚠️ 播放写线程停滞` 或 `⚠️ 麦克风读停滞` 告警 → 自动恢复
- 若出现第三种（冻结无恢复）→ 截日志再排查（按现有防御体系，理论上已不存在此路径）

## 6. 方法论小结

1. **日志缺口即信息**：三次都靠"打印停在哪一行"缩小范围——打断打印之后、播报被打断之前，就那么几个调用点
2. **复现要还原线程拓扑**：Timer 线程调 stop 不复现、mic 读线程调用才复现——"谁在什么状态下调用"和"调用什么"同样重要
3. **间歇性≠随机性**：三次不同调用点、同一族根因；认出"同族"后（与历史看门狗注释对上了），第三轮可以走推理定位而不必强求复现
4. **修复要问"这层守不住会怎样"**：第二轮修完没问"如果 abort 没生效呢"，导致第三次冻结；最终版每一层都独立兜底
5. **有界返回优于无限等待**：宁可放弃一个卡死的流（泄漏给 daemon），不让任何业务线程陪葬
