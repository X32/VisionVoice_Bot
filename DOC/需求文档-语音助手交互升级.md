# 需求文档：可交互智能语音助手升级

> 项目：learnPartner（学习伙伴）
> 基线：`src/chat/voice_chat.py`（已跑通 语音输入→ASR→LLM→TTS 闭环）
> 日期：2026-10-16
> 状态：待评审

---

## 1. 背景

当前 `voice_chat.py` 已实现完整的语音对话闭环：

```
麦克风 → VAD自动断句(silero) → ASR(SenseVoice) → LLM(qwen, 支持function calling) → TTS(matcha) → 扬声器
```

并解决了回声门控、SIGINT 硬退出、串行播报等工程难点。但它是"**开放麦克风 + 一问一答**"模式，距离可日常使用的智能助手还有 5 项能力缺口。

## 2. 现状与缺口总览

| #  | 能力                | 现状                                    | 缺口                   | 优先级 |
| -- | ------------------- | --------------------------------------- | ---------------------- | ------ |
| R1 | 唤醒词 + 会话状态机 | 开放麦克风，任何声音都触发识别          | 无唤醒机制，无状态管理 | P0     |
| R2 | 打断（barge-in）    | 播报期间用户语音被回声门控丢弃          | 用户无法打断机器人     | P0     |
| R3 | 流式响应            | LLM 全量生成完才 TTS，首响应延迟高      | 无流式管线             | P1     |
| R4 | 视觉交互            | VLM（Qwen2.5-VL）能力已有但游离在对话外 | "看看这是什么"走不通   | P1     |
| R5 | 真实设备控制        | 空调工具是占位字符串                    | 无真实执行通道         | P2     |

优先级依据：R1/R2 决定"智能音箱式交互"是否成立；R3/R4 是体验与差异化；R5 依赖硬件接入条件。

---

## 3. 功能需求

### R1 唤醒词 + 会话状态机（P0）

**问题**：当前任何环境声音（电视、旁人说话）都会被识别并送给 LLM，既浪费推理也产生误触发。

**需求**：

- FR1.1 支持固定唤醒词（如"小学习小学习"，具体词待定），唤醒前麦克风音频只做唤醒词检测，不进 ASR/LLM
- FR1.2 会话状态机：
  ```
  IDLE（只测唤醒词）
    → 唤醒词命中 → ACTIVE（提示音/应答，进入正常对话）
    → ACTIVE 下 30s 无有效语音 → 回 IDLE
  ```
- FR1.3 ACTIVE 状态下沿用现有 VAD→ASR→LLM→TTS 管线
- FR1.4 唤醒词检测本地运行（离线），不依赖网络
- FR1.5 误唤醒率与漏唤醒率可测量（提供测试样本集回放工具）

**技术候选**（评审时定）：

- sherpa-onnx keyword spotting（KWS，与现有栈同源，首选）
- openWakeWord / Porcupine（引入新依赖）

**验收标准**：

- [X] IDLE 状态下普通对话不触发 LLM 调用（离线回放验证：无关内容零误触发）
- [X] 唤醒词在 3m 内正常音量下唤醒成功率 ≥ 95%（待真机实测）
- [X] 状态切换有可观察的日志/提示音

**实施记录（2026-10-16）**：已完成。技术选型与实现见 `DOC/技术调研-R1唤醒词选型.md`。

- 新增 `src/voice_input/kws.py`（WakeWordDetector 封装，离线回放测试工具）
- `vad_asr.py` mic_loop 加 IDLE/ACTIVE 状态机（KWS 与 VAD 共用同一音频流）
- `voice_chat.py` 唤醒应答预合成 + `--wake-word/--no-wake/--wake-threshold/--active-timeout`
- 模型：`models/kws/sherpa-onnx-kws-zipformer-wenetspeech-3.3M-2024-01-01`（int8, epoch-99）
- 离线验证：TTS合成"你好伙伴"3种语速命中2种（带停顿的不中，属正常）；默认阈值0.25
- ⚠️ 离线回放测试需补≥1s尾部静音（流式模型需要尾随空帧才输出假设）

### R2 打断 barge-in（P0）

**问题**：TTS 播报期间回声门控丢弃所有音频，用户说"停"或插话补充都无效，必须等机器人说完。

**需求**：

- FR2.1 播报期间持续检测用户语音（与回声门控并存：需区分"扬声器回声"与"真人插话"）
- FR2.2 检测到用户插话后 ≤ 300ms 内停止当前播报
- FR2.3 打断后进入正常识别流程，用户的新指令进队列处理
- FR2.4 被打断的回复文本可选择记入历史（完整/截断，评审定）

**技术难点**：

- 扬声器单声道回声 vs 真人语音的区分：候选方案为
  a) AEC 回声消除（webrtc-audio-processing / speexdsp）后跑 VAD
  b) 能量+频谱启发式（简单但脆弱）
  c) 双麦克风（硬件支持才可行）
- 停止播报需与现有 `sd.play/sd.wait` 阻塞模型兼容（可能需换流式播放）

**验收标准**：

- [x] 播报中说出新指令，机器人 ≤ 0.5s 停止并开始听（离线验证：检测延迟0.16s+停播3ms；待真机确认端到端）
- [x] 机器人自己播报的回声不误触发打断（离线：纯回声零误触发，100/200ms延迟×0.3/0.6衰减全组合）

**实施记录（2026-10-17）**：代码完成，离线验证通过，待真机验收。方案见 `DOC/技术方案-R2打断barge-in-AEC.md`。

- **选型**：pywebrtc-audio（WebRTC AEC3，pip预编译wheel）；AEC3内置延迟估计器，`stream_delay_ms=0`即可，无需精确测ALSA延迟（离线验证hint=0与精确hint等价）
- **Phase A**（`src/voice_input/test_aec.py`，GO）：管线模式(HP+AEC+NS)+silero(阈值0.7, min_speech=0.06s)；残留-25~-37dB、误报0-0.3%、首触发0.07-0.16s。⚠️ 400ms以上延迟超AEC3规格（实际ChunkedPlayer声学延迟约70-130ms不受影响）
- **Phase B**（`src/tts/player.py`）：ChunkedPlayer分块流式播放，stop()经abort()实测3ms静音；R3可直接复用
- **Phase C**：`vad_asr.py`新增`feed_reference/set_playing/_barge_check`（播报期AEC消回声→silero→3连帧防抖→on_barge_in）；`voice_chat.py` worker改为合成(play=False)+流式播放，被打断回复记**全文+"（被用户打断）"**标记，打断后unmute短尾巴0.3s；CLI加`--no-barge-in/--barge-threshold`
- **设计不变量**：clean信号只用于打断判定绝不进主VAD/ASR；不打断时门控行为与改造前完全一致；播放路径弃用sd.play/sd.wait（规避C层互锁）
- 离线E2E（驱动真实`_barge_check`路径）：插话0.16s触发、纯回声0误触发

**R2.1 打断语义化（2026-10-17）**：已完成，离线全套 PASS，待真机验收。详见 `DOC/报告-R2.1打断语义化.md`。

- 背景：R2 判定"任何语音即停"，"嗯/对/好的"类听话反馈被误当成打断
- 改为双通道意图判定：**停止词KWS**（默认 不要说了/闭嘴+唤醒词，score=2.0）+ **长语音>1.2s**（新问题）；backchannel 零误触发
- 关键发现：KWS 必须喂**裸AEC**的clean（NS管线双讲谱处理毁音素识别）；语音场景后有状态污染，`set_playing(True)` 需重建AEC+KWS换新stream
- 修订：单词"停"KWS检不出（单音节限制），快停用"不要说了"；FR2.2 停止延迟目标改为 词长+0.3s（语义判定固有代价）
- 验证工具：`src/voice_input/test_barge.py`（backchannel/停止词/唤醒词/长语音/纯回声 五场景）

### R3 流式响应（P1）

**R3 流式响应（2026-10-19）**：已完成，离线全套 PASS（B/C/D 场景 + 回归），待真机验收。详见 `DOC/报告-R3流式响应.md`。

- 实现：`unified_llm.chat_stream`（ollama NDJSON / llama.cpp / OpenAI SSE 三端点，gen.close 即取消上游生成）→ `SentenceSplitter` 按句切分 → 合成线程逐句 TTS → `ChunkedPlayer.play_segments` 边合成边播（三线程两队列背压）；打断四处联动（delta循环/合成/播放迭代器/上游取消）
- 实测（离线，qwen2.5:7b 热态）：首 token 0.13s + 首句攒句合成 0.38s + primer 0.5s ≈ **首次出声 1.01s**（预算 2s）；句间写入 gap 0ms；打断后 0.31s 返回；`--no-stream` 可回退旧路径
- 流式期被打断的历史记录 = **已读文本 + "（被用户打断）"**（R2"全文+标记"的流式版：上游已取消，未读部分未生成完）

**问题**：当前首响应延迟 = LLM 全量生成 + TTS 全量合成 + 播放，长回答体感 5s+。

**需求**：

- FR3.1 LLM 流式输出（llama.cpp/ollama 均支持 SSE stream）
- FR3.2 TTS 按句/按块增量合成，边合成边播放（首包延迟目标 ≤ 1.5s）
- FR3.3 与 R2 打断联动：打断时立即终止上游 LLM 生成与 TTS 合成
- FR3.4 流式播放替代现有 `sd.play + sd.wait`（sounddevice OutputStream 分块写入）

**依赖**：与 R2 共用"流式播放"改造，建议同期实施。

**验收标准**：

- [x] 30 字回答的首语音延迟 ≤ 2s（本地网络）（离线实测热态 1.01s：首token 0.13+首句合成 0.38+primer 0.5；冷加载首token ~1.9s，需 ollama keep_alive 常驻；待真机确认）
- [x] 长回答听感连续，无句间长停顿（离线实测句间最大写入 gap 0ms，目标≤300ms）

### R4 视觉交互（P1）

**问题**：`camera_vlm_monitor.py` / `test_vlm.py` 已具备 Qwen2.5-VL 能力（llama.cpp @ 192.168.4.52:8080），但与语音对话管线完全脱节。

**需求**：

- FR4.1 新增工具 `take_photo_and_look(question)`：抓拍一帧 → 送 VLM → 返回描述，模型可自主决定调用
- FR4.2 用户说"看看我在干什么/这是什么"时，模型调工具并用语音回答
- FR4.3 与项目主线（学习监督，见 `DOC/pro.md`）打通：
  - 定时抓拍分析是否摸鱼（已有能力，10s 周期）
  - 摸鱼 ≥3 次语音提醒"集中注意力"
  - 连续学习 1h 无休息 → 语音提醒活动筋骨
- FR4.4 VLM 与文本 LLM 的后端可分开配置（VLM 是 llama.cpp 远程，对话 LLM 可能是 ollama）

**技术要点**：

- `unified_llm.LLM` 目前无图片消息支持，需扩展 image_url/base64 消息格式（llama.cpp 多模态接口）
- 摄像头抓拍是阻塞操作（warmup 5 帧），工具内需控制耗时（目标 ≤ 2s）

**验收标准**：

- [ ] 语音问"你现在看到什么"，5s 内给出基于实时画面的语音回答
- [ ] 摸鱼检测提醒按 pro.md 规则触发

### R5 真实设备控制（P2）

**问题**：`turn_on_air_conditioner` 返回固定字符串"小度小度--打开空调"，是占位。

**需求**：

- FR5.1 确定受控设备清单与协议（候选：ROS2 话题 / 红外编码 / 串口 / 米家等智能家居 API）
- FR5.2 工具执行结果真实反馈成功/失败，模型据实播报
- FR5.3 新增设备遵循现有三步注册（函数 + schema + TOOL_FUNCS）
- FR5.4 敏感操作（如关灯影响学习）可配置白名单/黑名单

**验收标准**：

- [ ] 语音"开空调"→ 真实设备动作，播报真实结果
- [ ] 失败时语音告知失败原因

## 4. 非功能需求

| 编号 | 需求                                                                    |
| ---- | ----------------------------------------------------------------------- |
| NFR1 | 全链路本地/局域网运行（ASR/TTS/LLM 均已本地化，唤醒词必须本地）         |

## 5. 实施建议与依赖关系

```
R1 唤醒词 ──────────┐
                     ├──→ R2 打断 ──→ R3 流式（共享流式播放改造）
                     │
项目主线(摸鱼监督) ──┴──→ R4 视觉交互（可独立先行）
R5 设备控制（等硬件条件，随时可插）
```

- **第一批**：R1（独立，先行）+ R4（独立，直接服务 pro.md 主线）
- **第二批**：R2 → R3（连续实施，共享播放层重构）
- **第三批**：R5
