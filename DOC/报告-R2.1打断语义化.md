# R2.1 打断语义化改造：方案与实施记录

> 项目：learnPartner ｜ 关联：`DOC/技术方案-R2打断barge-in-AEC.md`（前置）
> 日期：2026-10-17 ｜ 状态：离线验证全套 PASS，待真机验收

## 1. 问题与方案

**问题**：R2 的打断判定是"播报期间检测到任何语音就停"。用户听话时的自然反馈（反向通道 backchannel："嗯"、"对"、"好的"、"哈哈"）也被当成打断，播报频繁误停。

**方案**：打断条件从"检测到语音"升级为"检测到打断意图"，双通道判定（`vad_asr.py::_barge_check`）：

```
clean（AEC消回声后）
  ├─ 通道1 停止词KWS：检出 不要说了/闭嘴（唤醒词自动并入）
  │   → 短语说完即命中，立即停播（延迟≈词长+0.15s）
  ├─ 通道2 长语音：silero 连续语音 >1.2s（backchannel均<0.6s）
  │   → 用户在说新问题，停播转收听
  └─ 短且无关键词（"嗯/对/好的"）→ 两通道都不触发，播报继续
```

核心复用：R1 的 `WakeWordDetector`（wenetspeech KWS）加载第二个实例即为停止词检测器，零新增依赖。

## 2. 最终参数

| 参数 | 值 | 依据 |
|------|-----|------|
| 停止词表 | `['不要说了', '闭嘴', '别说了']` + 唤醒词 | 实测可靠性矩阵（见§4 P3/P6）|
| `keywords_score` | 全局 2.0，**别说了逐词 1.0** | 不要说了 1/2→2/2；别说了高分诱发'对'误触发（见P6）|
| 长语音阈值 | 1.2s | backchannel 最长 0.58s，触发实测 1.28s |
| KWS 分支 AEC | **裸 EchoCanceller**（无 NS/HP） | 见§4 P1 |
| silero 分支 AEC | AudioProcessor(HP+AEC+NS) | 保留 R2 结论 |
| `set_playing(True)` | **重建** AEC 实例 + KWS 换新 stream | 见§4 P2 |
| `player.stop()` | 只置事件，abort 异步 daemon 执行 | 见§4 P5（mic_loop线程同步abort会间歇性冻结）|

CLI：`--stop-words`（可多次）、`--barge-long-speech`、`--barge-kws-threshold`

## 4. 实施踩坑实录（按时间顺序）

### P1 KWS 在 NS 管线 clean 上全漏检 → 双分支 AEC

**现象**：停止词在 `_barge_check` 全漏，但同样的 KWS 在未处理音频上正常。

**定位**：层层解剖（独立KWS→NS后音频→真实管线clean），最后对比发现：NS 管线（HP+AEC+NS）的 clean 上 KWS 全漏（阈值降到 0.05 都不中），**裸 EchoCanceller 的 clean 上 0.25 即中**，且纯回声零误报。互相关检测显示管线 clean 里插话"能量在、波形畸变"——NS 在双讲时的激进谱处理破坏了音素级识别所需的频谱细节，而 silero 只做能量检测扛得住。

**解决**：双分支——KWS 喂裸 AEC 的 clean（保频谱），silero 喂 NS 管线的 clean（保能量检测稳定）。两个 AEC 实例各 0.1ms 构造、µs 级处理，开销可忽略。

### P2 语音场景后 KWS 漏检（状态污染）→ 每次播报重建

**现象**：单跑停止词场景命中；前面跑过任一含语音场景后，下一个停止词场景就漏。

**定位**：最小复现序列锁定（嗯→别说了 必失败，别说了→别说了 必成功）；组件隔离实验显示"单独换新 barge_kws 或单独换新 aec_kws 都能修复"——reset() 清不净的残留需要两个组件同时存在才致失败（AEC3 延迟估计器与 KWS 流状态的交互）。

**解决**：`set_playing(True)` 时**重建** AEC 实例（构造仅 0.1ms）+ KWS **换全新 stream**（`new_stream()`，创建零成本；KeywordSpotter 整体重建要 713ms 不可行，但解码状态在 stream 里）。

### P4 真机卡死：长语音打断后整个助手冻结（用户报告）

**现象**：真机打出"✋ 打断(long_speech)，停止播报"后系统冻结，不再响应。

**定位**：`stop()` 本身仅 1ms、worker 的 `play()` 正常返回——排除播放侧。复现拓扑（mic 读线程内调 stop + 输入流同时打开）第一次复现 mic 线程停滞 >6s，第二次不复现——**间歇性**。与代码库已记录的坑吻合（`voice_chat.py` 看门狗注释）："播放期间 Pa_ReadStream 会间歇性停滞，卡在 C 调用里永不返回"。该坑此前只影响退出（有 SIGINT 看门狗兜底）；R2 播放+打断常态化后在**运行中**触发，mic_loop 卡死 → `unmute` 永不执行 → 系统冻结且无自愈。

**解决**：读流与处理解耦 + 停滞看门狗自愈（`vad_asr.py`）：
- 新增 `_reader` 线程：阻塞读麦克风塞队列（停滞时该线程被放弃）
- `mic_loop` 带宽 2s 超时消费队列；停滞/读错 → 关流（daemon 关法防死锁）→ `_reset_listeners()` 清 VAD/唤醒/打断状态 → 重建 InputStream 继续
- 验证：假流模拟永久阻塞 → 9s 内 3 轮自愈、mic_loop 存活；真机 6s 冒烟无告警
- 附加收益：reader 常驻排空 ALSA 缓冲，识别耗时期间不再积压输入

### P3 停止词词表选型：单音节不可用，score=2 有奇效也有陷阱

**现象**：`停`/`停下` 全漏（0/2）；`别说了` 半稳（1/2）；`你好小迪` KWS 难命中。

**实验**：8 个候选词 × score{1,2} × 2 种回声的可靠性矩阵。结论：
- 单/双音节（停、停下）KWS 无法可靠检出——**不放词表**（文档明示 CLI 不要配单词）
- `不要说了` score=1 时 1/2 → score=2 时 2/2，且 backchannel/echo 误报 0
- `别说了` 在 score=2 下保持 1/2 且诱发 '对' 误触发 → 剔除（语义被不要说了覆盖）
- 唤醒词 KWS 不中无碍：长语音通道兜底
- 中途还踩了一个测试脚本 bug：词表矩阵实验忘了过 AEC 直接喂混音，所有词结果雷同（连纯回声都"命中"）——数据全噪声，重新加 AEC 后才得到真实矩阵

### P5 二次卡死（stop_word 打断后）与异步 abort

**现象**：真机 `stop_word:你好小迪` 打断后再次冻结——上次的读停滞看门狗（P4）没防住。

**定位**：这次卡点不在读流而在**写侧**：`on_barge_in` 在 mic_loop 线程里同步调 `player.stop()` → `stream.abort()`，该 C 调用在双工 ALSA 下**间歇性永久阻塞**（与 Pa_ReadStream 停滞同族）。看门狗只盯队列读取，防不住 `_barge_check` 内部的阻塞。

**解决（第一版）**：`stop()` 只置事件立即返回，`abort()` 扔进 daemon 线程。

### P7 三次卡死 → play() 有界返回（最终版）

**现象**：异步 abort 后真机 `stop_word:不要说了` 打断仍然冻结。

**定位**：abort 异步化只解决了"调 stop 的线程不被卡"，但**输出流本身已被 wedge**：worker 的 `stream.write()` 阻塞在 C 调用里永不出错（abort 未生效），`play()` 永不返回 → `unmute` 永不执行 → mute 窗口无限 → mic_loop 自愈也无效（音频全被门控丢弃）——系统静默假死。佐证：日志只见打断打印，无后续"播报被打断"。

**解决（最终版）**：`play()` 返回有界保证——实际写循环移入 writer 线程，`play()` 只等三态：写完 / stop（+150ms 宽限）/ **超时（音频时长+2s）**。任何情况（含 writer 被卡死）都在时限内返回，worker 得以 unmute 恢复收音。被卡死的 writer/流 daemon 化放弃，下次播报开新流。自测三态：正常 2.9s/3s、stop 即时返回、write 永久卡死 3.0s 超时逃逸。

**三次冻结的完整链条总结**：①读侧停滞（P4）→ reader线程解耦+自愈；②stop()内同步abort阻塞（P5）→ 异步abort；③write()被wedge的流卡死（P7）→ play有界返回。三个修复各挡一层，共同原则：**任何线程都不允许无限期阻塞在 PortAudio/ALSA 的 C 调用上，关键路径（unmute/收音）必须有超时逃生门**。

### P6 "停/停下/别说了不能打断"

- `停`/`停下`：单/双音节 KWS 检不出（矩阵实验 0/2），词表设计如此——快速停止请说"不要说了"
- `别说了`：高加分(2.0)会诱发"对"误触发被剔除过。本次启用 **KWS 逐词加分**（keywords.txt 原生 `:N` 后缀，`kws.py::_gen_keywords_file` 支持 `keyword_scores` dict）：`别说了` 以低加分 1.0 回归词表（1/2 召回、"对"零误触发），`不要说了`/`闭嘴` 维持 2.0 全召回

## 5. 真机验收清单（用户执行）

1. 播报中"嗯/对/好的" → 不打断
2. 播报中"不要说了/闭嘴" → 词说完后 ≤0.3s 停止
3. 播报中途开始问新问题 → ~1.3s 后停播并开始收听，问题被正常识别
4. 回归：正常对话、唤醒/休眠、Ctrl+C 正常

## 6. 遗留

- "停"单字快停不可用（KWS 限制）；若真机体验需要，候选方案是能量+音长启发式单独通道（未实施）
- 唤醒词打断依赖长语音兜底（1.2s+），不如停止词快；换唤醒词后可实测 KWS 命中率
- `drain_interrupted_audio()` 回补接口已就绪但 worker 尚未接线（stretch 项，待真机评估是否需要）
